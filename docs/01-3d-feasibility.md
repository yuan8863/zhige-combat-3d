## 0. 结论先行（如果只读一段）

**《止戈》的机制层几乎不依赖 2D，可以整体保留；真正需要重建的是"决策几何"与"表现层"，而这两块恰好是我现在这套原型最薄弱的地方。**

所以 3D 化的正确做法**不是**"把 2D 原型重写成 3D 游戏"，而是：

| 阶段 | 做什么 | 产出 | 风险 |
|---|---|---|---|
| **P0（已验证）** | 把规则与表现**解耦**：规则表、事件、反馈时刻表全部数据化；再加一个**俯视蓝图视图**验证几何 | 同一套 JSON 驱动 2D 与"上帝视角 2D" | 低 |
| **P1（2 周）** | 只换渲染层：Canvas 2D → Three.js，把"距离判定的 y 轴"接进来 | **能跑能打的 3D 单文件原型** | 中 |
| **P2（1 个月）** | 3D 才需要的新机制：Z 轴（横移）、朝向角、高低差、镜头 | 3D 版《止戈》可玩 demo | 中高 |
| **P3（不做，只写方案）** | 引擎迁移（Unity/Unreal）、动画资源、特效、网络同步 | —— | 高，已超出个人作品集范围 |

**一句话取舍：3D 化的收益主要在"表现力与第三人称临场感"，代价主要在"距离博弈的可读性"。** 白皮书第 2 层博弈（抢帧 / 距离管理）在 2D 是一条轴上的清晰问题，在 3D 会变成"球面问题"——**这是本次验证真正需要回答的问题，也是 §4 的核心。**

## 1. 先划清边界：哪些是 2D 特有的，哪些不是

我把自己现有的原型逐层拆开，判断每一层与 2D 的耦合程度。

| 层 | 当前实现（2D） | 与 2D 的耦合 | 3D 化时的处置 |
|---|---|---|---|
| **帧数据表**（起手/判定/收招/有利帧） | `BASE_MOVES` + 职业偏移，纯数值 | **无耦合** | **原样保留** |
| **有利帧推导** `有利帧 = 僵直 − (总帧 − 起手)` | 纯代数式 | **无耦合** | **原样保留** |
| **韧性 / 破防 / 架崩 / 处决** | 数值 + 状态机 | **无耦合** | **原样保留** |
| **杀势（Momentum）与困兽之斗** | 全局标量 + 阈值 | **无耦合** | **原样保留** |
| **伤害模型**（连段递减 / 贴身惩罚 / 霸体） | 纯数值 | 贴身惩罚用"距离" | 保留，但"距离"定义改为球面距离 |
| **状态机**（IDLE/WALK/ATTACK/DASH/HITSTUN/BREAK） | 6 状态 | 需要加"朝向状态"与"锁定状态" | **扩展** |
| **距离判定** | `Math.abs(def.x - atk.x) <= range` | **完全耦合** | **重做**（见 §3.1） |
| **攻击范围** | 一维线段 | **完全耦合** | **重做**（扇形/胶囊体） |
| **墙面 / 角落** | 左右两道墙 | **完全耦合** | **重做**（见 §3.3） |
| **AI** | `dirTo = sign(me.x - ai.x)` | **完全耦合** | **重做**（见 §3.4） |
| **表现层**（武器角度、位移、顿帧、震屏） | Canvas 2D 绘制 | **完全耦合** | **重写渲染，保留时刻表** |

**结论：白皮书里 8 个章节中，6 个是"数值与规则"，可以整段搬；只有"距离与几何"这一层必须重做。**

> 这一点值得在面试里讲清楚：**机制设计是否与维度无关，是判断"设计是否只是一个数值表"的分水岭。**
> 《止戈》的帧数据、有利帧推导、杀势系统在 3D 里一个字都不用改——因为它们描述的是
> **"两个决策之间的时间关系"**，而时间关系不依赖空间维度。

## 2. 3D 化的真实动机（以及不该做 3D 的理由）

### 2.1 做 3D 能得到什么

| 收益 | 说明 | 可否用 2D 替代 |
|---|---|---|
| **第三人称临场感** | 冷兵器竞技的"贴身压迫感"来自摄像机与角色的相对距离，2D 侧视天然削弱它 | ❌ 不可替代 |
| **Z 轴机动** | 横移/绕背使"绕后攻击"成为真机制（背击、侧击伤害区） | ❌ 不可替代 |
| **高低差** | 跳劈、下劈的伤害与帧数据可以做成新维度 | ⚠️ 2D 可用"上挑/落点"模拟一部分 |
| **受众预期** | 2027 届投递的岗位 JD 里有"虚拟世界架构师"，3D 是行业默认语境 | ❌ 不可替代 |
| **画面表现力** | 武器轨迹、布料、粒子在 3D 下的表现上限更高 | ⚠️ 需要预算，不是设计问题 |

### 2.2 做 3D 会失去什么（必须提前承认）

| 代价 | 说明 | 严重程度 |
|---|---|---|
| **距离博弈可读性下降** | 2D 里"距离"是一根轴上的一个数，玩家一眼可读；3D 里是球面关系，读距成本上升 | ⚠️⚠️ 高 |
| **帧数据的"确定性"被削弱** | 2D 的"闪避穿身"有唯一解；3D 下绕背/侧身让"是否命中"变成连续量 | ⚠️⚠️ 高 |
| **顿帧与判定的一致性更难保证** | 06 规范 §4.4 的"顿帧与有利帧一致性证明"依赖一维瞬时判定 | ⚠️ 中 |
| **工作量成倍** | 动画资源、摄像机、特效、性能预算，都不是一个人两周能补上的 | ⚠️⚠️ 高 |
| **仿真可复现性** | 现有仿真基于 1D 距离，3D 后需要新的仿真模型（否则"实测数据"失去意义） | ⚠️ 中 |

**我的判断：如果目标是"投递作品（证明我能设计战斗系统）"，3D 的边际收益低于它的成本；如果目标是"证明我能把系统落到工程与表现层"，那 3D 是必须走的一步——但应该走 P1/P2，而不是 P3。**

## 3. 分模块可行性验证

### 3.1 距离判定：从"一维线段"到"扇形 + 胶囊体"

**现状（2D）**

```
命中条件：|x_def − x_atk| ≤ range          // 一维
朝向约束：隐含（面朝方向决定攻击方向）
```

**3D 需要的判定（最小可行模型）**

```
命中条件：
  ① 平面距离   d_p = √(dx² + dz²) ≤ range
  ② 高度差     |dy| ≤ heightTolerance      // 建议 ±35px（≈半个身位）
  ③ 朝向夹角   cosθ ≥ cos(halfArc)         // 近战扇形，半角建议 55°~70°
  ④ 判定体     攻击者为"以朝向为轴、长 range、半角 halfArc 的扇形"
                 防御者为"半径 bodyR、高 bodyH 的胶囊体"
```

**关键设计问题：扇形的半角取多少？**

| 半角 | 手感 | 副作用 |
|---|---|---|
| 30° | 极度精确，几乎要求"对准" | 3D 下操作门槛过高，与"帧数据可读"的定位冲突 |
| **55°~70°** | **"大致对准即可"，容错来自角度而非时间** | 攻击会打到意想不到的敌人（3v3 下尤甚） |
| 90° | 近乎全向，等于是取消了瞄准 | 绕背/侧身失去意义 |

**建议取 60°，并用现有的"贴身惩罚"（长策 <70px 伤害 ×0.6）改造成"角度惩罚"**——
即：**夹角越大伤害越低**，把 3D 的角度不确定性变成一个可被玩家利用的连续旋钮，而不是一个非此即彼的命中/不命中。

> **这是本次验证最有价值的一条推论：3D 化会把"命中判定"从布尔量变成连续量，而连续量必须用"伤害/削韧系数"去承接，否则玩家会得到"我明明对准了却没中"的不公平感。**

### 3.2 时间层：帧数据可以原样保留

帧数据描述的是"决策之间的时间关系"，与空间维度无关。逐项核对：

| 机制 | 2D 实现 | 3D 是否可直接复用 | 备注 |
|---|---|---|---|
| 起手 / 判定 / 收招帧 | 表驱动 | ✅ 完全复用 | |
| 有利帧推导 | 代数式 | ✅ 完全复用 | `僵直 − (总帧 − 起手)` |
| 取消窗口与连段 | 帧计数 | ✅ 完全复用 | 连段动作换成 3D 动画，帧数不变 |
| 杀势阈值 30/60/90 | 标量 | ✅ 完全复用 | |
| 困兽之斗连续补偿 | 标量 | ✅ 完全复用 | |
| 顿帧时刻表 | 06 规范 §3.3 | ✅ 复用时刻表 | 但"冻结"含义要扩展（见 §3.5） |
| 抢帧顺序 | 起手帧大小 | ✅ 完全复用 | **3D 下抢帧的价值只增不减**（因为绕背更难抢帧） |

### 3.3 空间层：墙面与角落需要重新定义

**2D 的墙 = 一条线，3D 的墙 = 一个面。** 我在 v1.2 里已经用仿真实测过贴墙代价（**4.3pp**，见白皮书 §4.5），这个结论在 3D 下的对应问题是：

| 问题 | 2D | 3D | 处置建议 |
|---|---|---|---|
| 墙吸收击退 | 一维：击退量清零 | 三维：击退分解为法向（被吸收）+ 切向（滑走） | **切向滑走保留**，这是 3D 的新战术资源 |
| 角落 | 两端各一个 | 两墙夹角（凹角）、三面墙（真角落） | 墙角分级：**一面靠墙 / 双面夹角 / 三面死角**，代价递增（建议 3pp / 6pp / 10pp） |
| 绕背 | 不存在 | 存在 | 背击是否加成需要单独验证（建议先**不加成**，否则绕背会变成唯一解） |

> **"贴墙代价 4.3pp"这个数字在 3D 下不可直接采信**——它是在一维模型里测出来的。
> 3D 需要重跑一套"墙面几何"仿真，而不是把 2D 结论搬过去。**迁移文档里最容易犯的错，就是把旧维度的实测值当新维度的基线。**

### 3.4 AI：从"一维趋近"到"绕后 + 保持距离"

```javascript
// 现状（2D）：一维方向
const dirTo = Math.sign(me.x - ai.x) || 1;
ai.moveDir = dirTo;                 // 靠近
```

3D 的 AI 需要至少四个新行为：

1. **趋近**：移动到期望交战距离（不是简单靠近）；
2. **绕背**：在对方起手/收招期间改变方位角（用"方位角变化"替代 2D 的"左右横移"）；
3. **守距**：长策类职业需要主动维持 225px 交战圈（在 3D 里这是一个**圆环**，不是两个点）；
4. **闪避方向**：2D 的闪避是"前后"二选一，3D 是"以对方为圆心的任意角度"——
   这会让闪避从"猜方向"变成"猜角度"，**必须在动画上给出可读提示，否则手感会崩**（见 §3.5）。

> **可行但需要重做**：现有 AI 的决策参数（反应 / 格挡率 / 抢帧率 / 惩罚率）可以复用，
> 但"位置决策"部分需要重写。工作量估计：**2~3 人日**（不含调参）。

### 3.5 节拍 ×2 的配平结论：距离机制需要一条反制规则（v1.4 实测）
这一节不是 3D 专有，但它是 3D 迁移前必须先解决的问题——**因为 3D 会把"距离"从一条轴变成一片区域，
该机制的权重只会更高。**

v1.3 把动作节拍翻倍（时间轴 ×2）后，四职业配平崩了：长策对执锐稳定在 **80~90%**。
我扫了 11 组数值补偿（伤害、削韧、移速、防守强度、长策距离 225→200、击退 1.70→1.35……），
**全部无效**——把长策的距离和击退都收掉，它依然 88%。

**机理（三条推理，均有实测支撑）：**

1. 起手帧 ×2 后**所有攻击都变得可读**（12f/200ms > 人类反应阈值）→ 防守成功率整体上升；
2. 防守变强 → 单次进攻的期望收益下降 → **胜负从"谁打得准"转移到"谁能在防守中换取位置"**；
3. 位置博弈里，"**225px 判定区 + 击退 ×1.70**" 是全局最强工具 → 出现**永动风筝**：
   对手永远在判定区外侧，且每次接近都被击退推回。

**因此配平必须引入一条机制级反制，而不是继续拧数值。** 我采用的规则（v1.4）：

> **距离惩罚（Close-range Punishment）**
> **贴身缠斗会持续消耗长兵职业的韧性；当其韧性被打空后，会进入"兵刃脱手"状态——
> 攻击距离暂时缩短、伤害下降，直到恢复。**
>
> 这把"永动风筝"从"无解"变成"有代价"：长策每拉开一次距离都在冒风险，
> 而短手职业第一次拥有了"追上去就有回报"的确定性目标。

**这条规则与 3D 的关系（迁移提示）：**

| 维度 | 2D 实测（本轮） | 3D 需要重标 |
|---|---|---|
| 判定口径 | 单一距离阈值（如 <80px） | 应改为半径范围（贴身圈）——**3D 下"贴身"是一个圆**，不是一段 |
| 惩罚对象 | 长兵职业的韧性 | 不变 |
| 与角度的关系 | 无 | 可叠加"背身惩罚"（建议先不加，避免双重惩罚） |
| 与高低差的关系 | 无 | 高低差会改变"贴身"的可达性（跳劈 vs 站桩），需单独验证 |

### 3.5 表现层：动作曲线与顿帧的 3D 迁移

我在 v1.3 里给原型做了**三段式动作曲线**（蓄力 → 判定 → 收招，`SWING_CURVE` 数据表），
这套曲线**在 3D 下同样成立**，但要对齐两件事：

| 项 | 2D（v1.3 已实现） | 3D 需要补 |
|---|---|---|
| 蓄力 | 旋转 + 前倾偏移 | **重心位移**（上半身/下肢分离）+ 武器拖影起点 |
| 判定 | 快速甩过 + 12% 过冲回弹 | **武器轨迹为带状扫掠**（sweep），过冲改为轨迹超出目标 12% |
| 收招 | 余韵正弦衰减归位 | **脚部站位重新定位**（3D 下收招必须"落到位"，否则位移会漂） |
| 顿帧 | 冻结帧计数器（渲染自然跟着冻） | 沿用同一手法：**冻结逻辑时间轴，物理与布料继续跑**（06 规范 §9.1 已定义） |
| 慢镜 | 弹反/破防时 `slowmo` 减帧 | 同样可用，但摄像机的 **FOV 变化表（06 §6.2）在 3D 下是主要表现手段**，权重应上调 |

**关于"冻结"的 3D 版定义（沿用并扩展 06 §9.1）：**

> 冻结 = **动画时间轴 `speed = 0`，但物理（粒子、布料、次级动力学、武器拖影）继续。**
> 2D 下这是一句实现细节；**3D 下它是打击感的主要来源**——"人定住了，但身上的东西还在动"。

### 3.6 性能预算：60FPS 的 3D 帧预算怎么分

原型当前是**单文件 HTML + Canvas 2D**，在浏览器里跑 60FPS 毫无压力。3D 后需要重新分配 16.6ms：

| 项 | 预算 | 说明 |
|---|---|---|
| 逻辑（帧步进 + AI + 判定） | **≤ 2ms** | 现状：逻辑几乎不耗时，3D 判定（球面距离 + 夹角）略增 |
| 动画与骨架 | ≤ 3ms | 4 职业 × 6 招式 + 8 技能，建议用**骨骼动画 + 动作复用**而非逐招自定义 |
| 特效（拖影/粒子/命中光效） | ≤ 4ms | 06 规范 §2.2 的"反馈预算"B 档，3D 下粒子数应下调 30% |
| 渲染 + 后处理 | ≤ 6ms | 关闭阴影贴图的可选项、用简化描边替代 PBR |
| 余量 | ≥ 1.5ms | **必须留**，否则顿帧叠加时（3v3）必然掉帧 |

> **给面试官的一个具体判断**：3D 化后**顿帧的成本不再是"停止时间"，而是"停止时间 + 保持画面"**。
> 2D 下顿帧几乎免费（画面不动就是冻结）；3D 下顿帧期间仍需出帧（粒子继续动），
> 所以 **06 §4.3 的"3v3 顿帧叠加规则"必须重新标定**——否则团战顿帧会把帧预算吃光。

## 4. 本次验证最关键的一个问题：距离博弈在 3D 下还成立吗

白皮书把战斗拆成五层，其中第 2 层是**"距离管理：谁先进入判定区"**。
2D 下这个问题的答案是唯一的（`x` 轴上比较两个数）。3D 下变成：

```
2D：       A ──── dist ────▶ B          一维，可读
3D：       A 在 B 的某个方位角 φ、距离 d
           命中条件：d ≤ range 且 |φ| ≤ halfArc
           玩家的可读量：距离（大致）+ 方位（大致）+ 朝向（明确）
```

**三个必须在 3D 下重新回答的设计问题：**

| 问题 | 2D 的答案 | 3D 的风险 | 建议的验证方式 |
|---|---|---|---|
| **"贴近"是否仍然是优势？** | 是：贴身区 0~60px 双方都能秒中 | 3D 下贴身容易被绕背，可能变成劣势 | 用 2D 原型加"方位角"仿真：把 `|dx|` 改成 `√(dx²+dz²)`，扫 halfArc 参数 |
| **绕背是否应该加成？** | 不存在 | 若加成，会挤压"抢帧"这条主轴；若不加成，绕背无收益 | 先不加成，用仿真验证"绕背本身的命中收益"是否已足够 |
| **闪避方向的信息可读性** | 前后二选一 | 任意角度 → 玩家无法预判 | **必须在动画上做可读提示**（06 §6 摄像机 / 蓄力光效） |

**可以用现在的原型零成本做的验证（P0 阶段）：**

我现在的原型已经有 `_一致性核验.js` 和仿真脚本，加一个"蓝图俯视模式"（把 `x` 轴渲染成 `x-z` 平面）
就能在**不改逻辑**的前提下，先看 3D 的距离关系长什么样：

```
原型新增（约 40 行）：
  1. 增加 fighter.z（默认 0），移动输入增加 KeyW/KeyS 映射到 z
  2. 命中判定：dist = Math.hypot(def.x - atk.x, def.z - atk.z)
  3. 增设"俯视蓝图"渲染：把 x-z 画成平面网格，用扇形画出攻击范围
  4. 面板显示：距离 / 方位角 / 是否在扇形内
```

**这就是我建议的第一步：不等引擎，先用现有原型的"上帝视角"验证 3D 的几何是否更好玩。**
成本约 1 天，风险接近零，而且**失败也有产出**（一套可复用的几何验证工具）。

## 5. 三条路线与推荐

| 路线 | 做法 | 成本 | 产出 | 建议 |
|---|---|---|---|---|
| **A. 2D 强化（不做 3D）** | 继续深化现有原型（学到的都能验证） | 低 | 现在这份作品集 | 若目标是"证明设计能力"，够用 |
| **B. 渲染层 3D 化（Three.js）** | 逻辑不动，只换渲染 + 补 Z 轴 | 中（1~2 个月） | 单文件 3D 可玩原型 | **推荐**：性价比最高，且保住"单文件可玩"这个优势 |
| **C. 引擎迁移（Unity/Unreal）** | 用商业引擎重做 | 高（3~6 个月 + 需要美术） | 真 3D 项目的起点 | 不建议作为作品集阶段目标 |

**推荐 B 的理由：**

1. **可玩性不打折**：仍然是"双击就能玩"，这句话在面试里价值极高（对方 30 秒内能看到东西）；
2. **可验证性不打折**：帧数据、有利帧、杀势全部原样保留，现有的 4 道自动校验关卡继续有效；
3. **工作量可控**：逻辑层零改动，渲染层重写约 800~1200 行；
4. **可退回**：如果 3D 手感验证失败，2D 版本仍在仓库里，且两者共用同一套数值表。

## 6. 分阶段计划与验收标准

| 阶段 | 交付物 | 验收标准 | 预估 |
|---|---|---|---|
| **P0** | 蓝图俯视模式 + 3D 几何仿真脚本 | 能回答 §4 的三个问题；扇形半角有数据支撑 | **1 天** |
| **P1** | Three.js 单文件 3D 原型（4 职业 × 24 招式） | 60FPS 稳定；帧数据与 2D 版逐字段一致（脚本核验）；能完整打完一局 | 2 周 |
| **P2** | Z 轴机动 + 朝向 + 绕背 + 镜头规范 | 3D 特有的"方位博弈"可被玩家描述；AI 能在 3D 下合理交战 | 3~4 周 |
| **P3** | 引擎方案书（不实施） | Unity 侧的资源/动画状态机/网络同步方案文档 | 1 周 |

**每一阶段的硬门槛（沿用现有纪律）：**

1. **帧数据必须三方一致**（`_verify.py` / `_一致性核验.js` 继续跑，3D 版不得改任何帧数）；
2. **60FPS 不允许用"掉帧换表现"**（顿帧叠加场景必须实测）；
3. **距离/命中判定的任何改动都必须有仿真数据支撑**（禁止"感觉更好"）。

## 7. 局限与不做的事（诚实声明）

- **本文档不是"我已经做了 3D"**，而是"我验证了能不能做、代价是什么、先做哪一步"；
- **3D 下的平衡数据一律缺失**：现有的 P1~P5 全部基于 1D 距离模型，3D 后需重跑；
- **没有美术资源**：P1 阶段只能用几何体 + 描边（这也是我建议先做 P1 而不是 P3 的原因）；
- **没有多人同步**：3v3 的 3D 版本涉及网络同步与帧同步选型，本文档只给方向不给结论；
- **摄像机规范尚未按 3D 重写**：06 规范 §6 是 2D 侧视基线，3D 需要新的取景与冲突处理规则。

> **我认为这份验证最有价值的部分不是"3D 可行"，而是把"哪些是维度无关的、哪些不是"分清楚了。**
> 一个战斗系统设计能不能迁移到 3D，取决于它的核心是不是"时间与决策"，
> 而不是取决于它画在几张坐标轴上。
